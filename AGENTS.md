# Agent Instructions: Geeta Homestay

Live production booking app. Frontend: React + Vite + Tailwind (Vercel).
Backend: Node.js + Express + MongoDB (Render). Payments: Razorpay.
Auth: Google OAuth, JWT in an httpOnly `accessToken` cookie.

## 1. Context Protocol

1. BEFORE any code change, read PROJECT_CONTEXT.md. Do not re-scan the
   whole codebase if it already answers the question.
2. AFTER any change that adds, removes, or modifies a feature, API
   endpoint, data model, or architectural pattern, update the affected
   section(s) of PROJECT_CONTEXT.md in the same task, before marking
   it complete.
3. Keep updates surgical: edit only the affected rows or sections.
4. Trivial changes (typos, formatting, no-behavior refactors) do not
   require a PROJECT_CONTEXT.md update.
5. If PROJECT_CONTEXT.md and the code disagree, trust the code, fix
   the doc, and tell me about the discrepancy.
6. Never print, log, or write secret values (API keys, JWT secret, DB
   credentials, webhook secrets) anywhere, including
   PROJECT_CONTEXT.md. Reference env var names only. Never commit
   .env files.

## 2. Production Safety

Flag any change to auth, payment routes, or middleware as
"SECURITY-RELEVANT" before applying it.

### Default auth posture: require login by default
- Every backend route uses `requireAuth` unless it serves genuinely
  public, non-user-specific data. Current public routes: `/status`,
  `/allRooms`, `/testimonials`, `/auth/google`, `/payment/getKey`.
- Never weaken `requireAuth` or remove auth checks without explicit
  confirmation.
- Never introduce an "optional auth" pattern (continuing without
  `req.user`) without asking me first. If unsure whether a route
  should be public, default to protected and flag it.
- Exception: webhook endpoints called by third parties (e.g.
  Razorpay) authenticate by verifying the signature of the raw
  request body, not by `requireAuth`.

### Identity and ownership
- Identity always comes from `req.user.id` (verified JWT). Never trust
  a `userId` from the request body, query, or chat text.
- For any route that acts on a resource by ID (bookings, payments,
  invoices): fetch the resource first, compare its real owner to
  `req.user.id`, return 403 on mismatch, and only then act.
- Ownership checks must run BEFORE any call to a third-party API
  (Razorpay, email).
- Booking lookups accept either the document `_id` or the group
  `bookingId`. Use the shared `$or` resolution, not a single field.

### Payments
- Amounts are always computed server-side from DB prices, nights, and
  quantity. Never trust an amount, price, total, or discount sent by
  the client or generated by an LLM.
- Verify the Razorpay signature, and verify the paid amount against
  the server-computed expected amount, before confirming bookings.
- Confirmation logic lives in one shared helper. Do not write a
  second copy.
- Never log full payment payloads, signatures, or card details.

## 3. Editing Rules

- Put new features in new files (e.g. a new controller) rather than
  editing inside existing, hardened functions. Do not touch unrelated
  functions in a file.
- After editing any backend file, run `node --check <file>` and show
  me the output. Before reporting done, confirm the server boots with
  `npm run dev` and no errors.
- Do not run `git commit` or `git push` unless I ask. Do not change
  git history.
- Frontend tasks marked "UI only" must not change data-fetching,
  auth, cart, or payment logic.

## 4. Testing and Reporting

- Never claim something is fixed without evidence. Report real HTTP
  status codes, response bodies, and DB state, not summaries.
- When a task says "report, don't fix", report findings only and
  change nothing.
- Never run tests against the production database. Use a separate
  test database, and ask before deleting any test data.
- Delete temporary test scripts when finished, and confirm they are
  not tracked by git.

## 5. Frontend Conventions

- Style: minimalist, professional, not template-looking. Use the
  existing palette (teal, terracotta, cream), existing fonts, and the
  existing card style, as documented in PROJECT_CONTEXT.md section 8.
- Responsiveness: use the breakpoints already in
  `tailwind.config.js`. Do not invent new ones.
- Reuse existing components (LoadingCard, SkeletonRoom, status
  ribbon) instead of creating duplicates. New shared components go in
  `frontend/src/components/` in PascalCase.

## 6. Hosting Awareness

- Backend runs on Render (free tier cold starts, ~30 to 60 seconds).
  Do not add heavy work at startup. Connect to MongoDB once at boot
  and reuse the connection.
- Backend and frontend deploy separately. If an API contract changes
  (for example, `/payment/checkout` now takes `bookingId`), say so
  explicitly so both sides can be deployed together.
